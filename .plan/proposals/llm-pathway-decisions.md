## 事项一：失败策略（重试与回退阈值）

### 背景【实证】

单次 LLM 调用的失败源不少且**真实发生率不低**：网络/网关断连（novel 实证的半开连接问题，已用 DisableKeepAlives 缓解但仍在）、**账号限流**（今晚我们自己的调研代理就撞了一次 1302 限流）、JSON 围栏剥离后仍解析失败（模型偶发不守格式）、超时。

### 选项与影响

| 选项 | 行为 | 影响 |
|---|---|---|
| A 立即回退 | 单次失败即任务回退+need_intervene | 最简单、最快暴露问题；但网络抖动一次就打断流程，可用性差【推断：单次失败率足以频繁打断】 |
| **B 有限重试→回退（推荐）** | 指数退避重试 **6 次**（novel 真机实证值，worker 退避骨架直接 copy）仍失败 → 任务回退（exec 重入语义，rolled_back_count++）+ need_intervene 置位 → 收件箱人工接管；`retry_max` 参数化进 config | 抖动/限流自愈；确定性错误（prompt 坏）6 次后快速放行给人工；参数可调 |
| C 无限重试 | 不设上限，重试到成功 | outbox 无限重试的先例理由是「通知必须送达」——LLM 产文失败可能是**确定性**的（prompt/配置坏），无限重试会永久空转占资源，语义不同，不推荐 |

### 推荐

**B**，`retry_max=6`（参数化，config 可改）。回退后的人工接管入口零新机制：need_intervene 收件箱投影（现有）+ 人工修复后 wb_assign_task 重新派发（现有）。

## 事项二：执行形态（同步 vs 异步）

### 背景

节点激活后，produce/review 的 LLM 调用在**哪个时机、由谁等待**：
- **同步**：HTTP 请求（wb_advance 等）内直接调 LLM，调用方等返回（timeout 120s）。
- **异步**：节点激活 = 派发任务 → 后台调 LLM → 产出入库（wb_add_artifact，-K）→ `wb_task_update complete` 走既有判据链推进。

### 选项与影响

| 选项 | 行为 | 影响 |
|---|---|---|
| A 同步 | 请求内等 LLM | 调用方挂最长 120s；超时后状态不明（任务是否已建？）；与既有「完成信号双通道：长任务=响应者调标准完成接口」设计相悖；qa_drive 驱动模式要改 |
| **B 异步（推荐）** | 激活=派发任务（wb_assign_task，executor=节点执行角色）→ 后台 goroutine 调 LLM → 入库 → complete 上报 → 判据链推进 | 与既有完成上报通道**完全同构**（零新机制）；HTTP 不阻塞；超时语义清晰（失败走事项一的策略）；qa_drive 驱动模式零改动 |

### 推荐

**B 异步**。它就是现有「完成信号双通道」设计的自然延伸：LLM 后台任务 = 一个特殊的「响应者」，按既有协议上报完成。超时参数沿用 novel 的 `timeout_sec: 120`；模型默认 `deepseek-v4-flash`（配置可换）。

## ✅ 拍板结果（2026-09-12，已开工）

- **事项一：B+**——退避重试 6 次（参数化）→ 回退+need_intervene；**用户追加两条**：①scanner 轮询发现异常中断的任务（服务重启等导致停滞）→ **继续任务**（恢复执行，非回退）；②**单任务多次失败 → 告警**（通知 + need_intervene）。
- **事项二：B 异步**——激活=派发任务 → 后台调 LLM → 产物入库 → complete 走判据链。
