# M5 PRD：版本管理（版本 CRUD + 版本状态机 + 版本进度汇总）

> 里程碑：M5
> 状态：**v1.0（已确认决策）**
> 依赖：M3 版本筛选/看板 + M4 需求增删改（编辑表单已有 versionId 下拉）；可视化参考 `docs/prototype/m5-version-prototype.html`
> 实现载体：`wbflow-1` 插件（pkg-9 起，Host 加版本写接口 + Client 加版本管理 UI）

---

## 1. 目标

把 M3 的**只读版本筛选**升级为**可维护的版本体系**：
- **版本 CRUD**：新建版本 / 编辑版本名 / 删除版本
- **版本状态机**：每版本有 `待启动 / 进行中 / 已发布 / 已废弃` 四态，支持**推进**（前进一格）与**废弃**（任意阶段直接废弃）
- **版本进度汇总**：每个版本的需求数 + 各状态分布（待启动/进行中/已完成/已取消）
- 需求归入版本：**沿用 M4 编辑表单的版本下拉**（不加快捷入口——推进主要靠 agent 工具，UI 保持简单）

**不包含**（后置）：版本恢复/回滚（v1 废弃不可回滚）、迭代排期/燃尽图、版本间需求批量迁移拖拽、真实子 agent 拆版（M7）。

---

## 2. 数据模型

沿用 `versions.json`（单文件数组）+ `requirements.json`（`versionId` 关联）。**每条版本新增 `state` 字段**。

```json
[
  { "id": "v-1", "name": "v1.0", "state": "进行中", "isBacklog": false },
  { "id": "v-11", "name": "v1.1", "state": "待启动", "isBacklog": false },
  { "id": "v-backlog", "name": "待分配", "state": "待启动", "isBacklog": true }
]
```

| 字段 | 说明 |
|---|---|
| `id` | 稳定短码 `v-<n>`；`v-backlog` 固定为「待分配」保留项（**不可删/不可改名/无状态操作**） |
| `name` | 展示名（**自由文本**，如 `v1.2`、`2.0 迭代`） |
| `state` | **版本状态**：`待启动 / 进行中 / 已发布 / 已废弃` |
| `isBacklog` | 是否待分配池（仅 `v-backlog` 为 true） |

- 新建版本：`id = 'v-' + (max 序号+1)`，`name` 必填，`state=待启动`，`isBacklog=false`；
- 需求 `versionId` 指向版本 `id` 或 `v-backlog`（待分配）。

### 2.1 版本状态机（v1 已确认）

```
待启动 ──推进──▶ 进行中 ──推进──▶ 已发布
   │                │                │
   └── 任意阶段直接「废弃」 ──────────┘
              ▼
           已废弃（终态，v1 不可回滚）
```

| 当前态 | 推进目标 | 说明 |
|---|---|---|
| 待启动 | 进行中 | 开始该版本迭代 |
| 进行中 | 已发布 | 版本交付（**不阻止**：存在 bugfix 需求时也可发布，仅提示未完成需求数） |
| 已发布 | — | 无推进目标 |
| 任意态 | 已废弃 | **任何阶段可直接废弃**：二次确认后执行，其下所有需求 `status → 已取消`；**v1 不可回滚**（恢复/按审计回滚后置） |

> 废弃动作：弹**二次确认**「废弃后版本下 n 条需求将全部转为已取消，且 v1 不支持恢复，确定？」；确认后：版本 `state=已废弃` + 该版本下所有需求 `status=已取消`（同时这些需求的 `updatedAt` 刷新，**不写** `history`——状态联动非人工编辑，后置审计记录）。

### 2.2 发布软约束（已确认）
- `已发布` 时若该版本下仍有未完成需求（待启动/进行中）：**仅提示不阻止**（bugfix 需求场景）。

## 3. 页面与交互

### 3.1 版本管理入口
- 顶栏（版本筛选下拉旁）加 **「版本管理」按钮**（中性色）；
- 点击打开 **版本管理弹窗**（模态框，风格同表单弹窗，可叠加在任意视图上）。

### 3.2 版本管理弹窗（核心）
- **版本列表**：每个版本一行，显示：
  - 版本名 + 状态徽标（彩色）+ 需求数；
  - **进度汇总**：`待启动 n · 进行中 n · 已完成 n · 已取消 n`（彩色圆点 + 计数）+ 进度条；
  - 行尾操作：**推进按钮**（`▶ 推进`，待启动/进行中显示；已发布/已废弃隐藏）· **废弃按钮**（`✖ 废弃`，任意非废弃态显示）· ✎ 改名 · 🗑 删除；
  - `v-backlog` 待分配池：锁定（仅显示，无操作）。
- **「＋ 新建版本」**：顶部输入框 + 按钮 → 创建（state=待启动）→ 立即出现在列表与顶栏筛选下拉。

### 3.3 版本改名 / 删除
- 改名：行内小弹窗输入新名（自由文本）→ 保存 → 顶栏筛选与需求卡片同步更新；
- 删除：**有需求引用时禁止**（提示「该版本下还有 n 条需求，请先移出」）；无引用直接删除。

### 3.4 需求归入版本（已确认：不加快捷入口）
- 仅 M4 编辑需求表单的「版本」下拉；版本管理弹窗不做批量迁移。
- **推进/废弃主要靠 agent 工具**（`wb_advance_version` / `wb_deprecate_version`，见技术设计），UI 只是辅助入口。

### 3.5 版本筛选联动
- 新建/改名/删除/状态变更后，顶栏「版本」下拉即时刷新（重新拉 `wb.listVersions`）。

## 4. 已确认决策（User 回复）

1. **状态机**：单向推进（待启动→进行中→已发布，不可回退）；**任意阶段可直接废弃**；废弃后其下需求全部转已取消；**废弃二次确认**；**v1 不支持恢复/回滚**（恢复按审计回滚后置）。
2. **发布约束**：不阻止（bugfix 需求场景），仅提示未完成需求数。
3. **删除规则**：有需求引用禁止删除。
4. **归入版本**：不加快捷入口，编辑表单下拉即可（推进主要靠 agent）。
5. **进度汇总**：按现有（计数 + 进度条）。
6. **版本名**：自由文本。

## 5. Host 写接口（新增）

| 方法 | 入参 | 出参/副作用 |
|---|---|---|
| `wb.createVersion` | `{ name }` | 追加版本（id 递增，state=待启动，isBacklog=false）→ `{ ok, verList }` |
| `wb.updateVersion` | `{ versionId, name }` | 改名（自由文本；`v-backlog` 拒绝）→ `{ ok, verList }` |
| `wb.advanceVersion` | `{ versionId }` | 状态推进一格（待启动→进行中→已发布；`v-backlog`/已废弃拒绝）→ `{ ok, verList, error? }` |
| `wb.deprecateVersion` | `{ versionId }` | 废弃：版本 state=已废弃 + 其下需求 status→已取消 → `{ ok, verList, reqList, depCount }` |
| `wb.deleteVersion` | `{ versionId }` | 有需求引用 → `{ ok:false, blocked:true }`；无引用删除 → `{ ok, verList }` |
| `wb.listVersions` | — | 已有（M3），返回最新列表（含 state） |

> 全部走 `writeJson('versions.json' / 'requirements.json', ...)` + `writePolicy()`；返回值纯 JSON（lossless 铁律）。
> `deprecateVersion` 需同时写两个文件（versions + requirements）——同一需求联动写两文件，失败语义：先写 versions 后写 requirements，任一失败返回 error（mock 阶段不引入事务）。
