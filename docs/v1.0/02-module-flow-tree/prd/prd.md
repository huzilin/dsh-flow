## 1. 问题陈述（为什么做）

### 1.1 现状与证据

平台的核心价值在于把流程推进、评审沟通、产物阅读与门禁收敛进需求详情页。没有流程树，需求就无法按阶段流转、评审无法闭环。

### 1.2 影响与代价

缺乏流程树 → 需求无法有序推进；缺乏评审对话 → 门禁形同虚设；缺乏锚点评论 → 沟通无法精确到产物位置。

### 1.3 时机与约束

模块 II 是价值核心，须在 MVP 落地；与制度层（流程/角色/门禁）和执行层（wb_my_task）联动。

## 2. 目标与成功指标

### 2.1 业务结果指标

| 指标 | 当前基线 | 目标值 | 观察周期 | 数据口径 |
|---|---|---|---|---|
| 评审闭环 | 无 | 全评论 resolved 才可通过 | — | 门禁判定通过 |
| 需求可推进性 | 无 | 节点通过前进/打回回退 | — | 状态机转移 |

### 2.2 交付结果指标（护栏 Guardrails）

| 指标 | 底线要求 |
|---|---|
| 门禁前置校验 | 未闭环时 decide/review 返回 blocked，不静默通过 |
| 锚点不失效 | 行级锚点防漂移（lineText 指纹四步定位，失效标「⚠」） |

## 4. 用户与场景

### 4.1 用户角色

| 角色 | 特征 | 目标 |
|---|---|---|
| User | 评审/最终决策者 | 评审产物、参与讨论、强权干预、拍板推进 |
| 角色子 agent（RD/FE/QA/CR…） | 产出者/评审者 | 产出产物、回复评审、表态 |

### 4.2 主路径

点击模块 I 需求卡 → 进入需求详情页 = 流程树 → 左列节点全展示，右列当前节点详情（元信息/评审状态行/产物/门禁）→ 点产物文件行打开阅读器 → 选择行级/范围/块级锚点评论 → 评论闭环后「通过」推进下一节点。

### 4.3 高频异常场景

- 无产物节点 → 显示「尚无产物」占位，不拦流程 UI。
- 锚点失效 → 就近展示并标「⚠ 锚点可能失效」，用户重新确认后更新。
- 拉锯（roundCount > 5）→ 自动通知 Leader/User 介入。
- 待复核挂起 → 超时提醒提评者复核。

## 5. 功能需求

### 5.1 功能总览

| 功能模块 | 优先级 | 描述 | 状态 |
|---|---|---|---|
| 流程树 | P0 | 左列节点全展示，节点独立前进/回退 | 待开发 |

### 5.2 功能详细说明

#### 流程树（左列）

**用户故事**：作为 User，我希望竖向查看流程全部节点，以便掌握需求在各阶段的状态。

**交互流程**：节点按流程序排列，全展示不折叠；每节点一行 = 状态圆点（绿=已通过/黄=进行中|待评审/灰=未开始）+ 节点名 + `↩N`（回滚 N 次）→ 点击切换右列详情。

**业务规则**：节点独立（一条流程标签=一个节点，可独立回退重入）；通过→前进下一节点；打回→回退上一节点（并行组内打回按 targetBranch 部分回滚）。

**验收标准（AC）**：
- [ ] Given 有流程数据, when 进详情, then 左列展示全部节点（含已通过/未开始）。
- [ ] Given 节点通过, when 确认, then 当前节点前移下一节点。
- [ ] Given 打回, when 带理由, then 回退上一节点（并行组 targetBranch 部分回滚）。

#### 节点详情（右列）

**功能描述**：右列固定四区：元信息 / 评审状态行 / 产物 / 门禁。

**用户故事**：作为 User，我希望在当前节点查看元信息、评审状态、产物与门禁，以便推进评审。

**交互流程**：元信息卡（负责人/进入时间/回滚次数/职责）→ 评审状态行（角色药丸）→ 点角色药丸展开「意见↔反馈」对话区 → 产物区（文件行 + 💬N）→ 门禁区（评论 2/6 + 通过/打回按钮）。

**业务规则**：`reviewers` 与 `gate` 均无的节点只显示元信息与产物；角色状态为派生值（该角色评论全闭环才算已通过）。

**验收标准（AC）**：
- [ ] Given review 节点, when 渲染, then 显示评审状态行 + 门禁区。
- [ ] Given 非 gate 节点, when 渲染, then 不显示门禁区。

#### 评审状态行与角色对话区

**用户故事**：作为 User，我希望展开角色对话串，以便参与讨论、解决与强权通过。

**交互流程**：角色药丸行 `Architect ✅` / `RD ✅` / `FE ⚠2` / `QA ⚠轮14` → 点开该角色「意见↔反馈」对话区（一条评论一条对话串，可多轮 roundCount）→ User 三态：参与讨论（回复）/ 普通 resolve / 强权 override。

**业务规则**：轮次 ≥10 未解决 → 药丸黄色高亮「疑似卡死」；评审通过 = 该角色名下全部评论 resolved/overridden；override 把该角色所有 open 评论置 overridden。

**验收标准（AC）**：
- [ ] Given 角色有 open 评论, when 点药丸, then 展开该角色对话区。
- [ ] Given 评论轮次 ≥10 未解决, when 渲染, then 药丸黄色高亮。
- [ ] Given 点「强行通过 X 全部剩余」, when 确认, then 该角色 open 评论全 overridden。

#### 产物阅读器

**用户故事**：作为 User，我希望点产物打开阅读器，以便在正文精确位置评论。

**交互流程**：点文档产物文件行 → 弹窗约 72vw×85vh（正文占满宽度，无右侧栏）→ 底部固定输入框 → 单击行=单行选中、点其他行=框选范围、重复点起点=取消、框选后再点=重新开始 → 输入框文案随选中状态变化。

**业务规则**：轻量 Markdown 渲染（标题/粗体/行内代码/围栏代码块整体渲染+语言标签；mermaid 仅按代码块展示不画图）；每行左侧灰色行号（1-based）；line 锚点展示于对应行下方、range 只在末行显示一次 + `↔A~B` 标记、block 显示于代码块下方、document 显示于正文末尾。

**验收标准（AC）**：
- [ ] Given 点文档产物, when 打开, then 阅读器渲染正文 + 行号 + 底部输入框。
- [ ] Given 选择一行, when 发表, then 生成 line 锚点评论。
- [ ] Given 框选范围, when 发表, then range 评论只在末行显示一次 + `↔A~B` 标记。

#### 评论展示与操作

**用户故事**：作为 User，我希望评论可回复/解决/强制通过，以便闭环评审。

**交互流程**：评论卡片 = 作者 + 文本 + 状态标 + roundCount；open 态常驻「回复」+「解决」按钮；已解决默认折叠为一行摘要，点击展开。

**业务规则（UI 操作判定矩阵，m7 §6.1）**：一条评论的操作面板按「状态 × 操作者」动态渲染。

| 评论状态 | 操作者 | 可操作 | 判定 |
|---|---|---|---|
| open | 任何人 | **回复**（reply） | 继续讨论/提问/澄清，状态不变（roundCount++） |
| open | **assignee**（缺省 = 锚定产物作者；QA 缺陷 = 显式指派 RD\|FE） | **resolve（A 修复关闭）** | 已修复 → 填 note → 转 `pending-confirm` |
| open | **提评者**且讨论已一致 | **resolve（B 协商一致关闭）** | 达成一致 → 填 note → 直接 `resolved` |
| open | 非 assignee 非提评者 | 仅回复 | 表达意见，等 assignee/提评者收尾 |
| pending-confirm | **提评者** | **confirm / reopen** | 最终裁定（复核不通过 reopen → open） |
| pending-confirm | 非提评者 | 只读 | 等待提评者复核 |
| resolved / overridden | — | 只读 | 可展开查看 resolve 记录（by/note/path） |

- 判定一句话：**reply** = 评论未关还想说；**resolve** = 要关——你修复了（A）或谈拢了（B），必须填 note；**confirm/reopen** = 已 resolve 过、你是提评者做最终裁定。
- **User（协调者）特判**：可代任一身份操作（代 assignee 走 A、代提评者走 B 或 confirm/reopen），**操作前须指明扮演角色**（操作归属记到被代者名下），避免身份混淆。
- **重复问题不合并**：同锚点 = 不同问题，各自独立 thread/resolve，不合并。
- 评论**不可编辑/删除**；误发用 reply 标注「作废」（审计留痕）。

**验收标准（AC）**：
- [ ] Given open 评论, when assignee 修复, then 转 pending-confirm 待提评者复核。
- [ ] Given pending-confirm, when 提评者 confirm, then 转 resolved（门禁放行）。
- [ ] Given 提评者 reopen, when 复核不通过, then 转 open（roundCount++）。

#### 门禁（通过 / 打回 / 强权 / 新范围）

**用户故事**：作为 User，我希望门禁通过/打回，以便推进或回退流程。

**交互流程**：门禁 = 该节点全部评论闭环；UI 常驻展示 `已解决/总数`（如 2/6），未满时「通过」置灰/拦截；打回必填理由 + 可选新范围界定；强权 override/forceRevise 由 User 明确指令触发。

**业务规则**：通过为终审，前置校验通过后节点→已通过、currentNodeId 前移；打回 reason 必填、节点回退；`defineScope` 关闭 pendingScope 写入新范围边界。

**验收标准（AC）**：
- [ ] Given 门禁未满, when 点通过, then 置灰拦截（blocked）。
- [ ] Given 门禁全闭环, when 点通过, then current_node_id 前移。
- [ ] Given 打回, when 无理由, then 拒绝。

#### QA 验收：缺陷闭环（验收节点特有交互）

**用户故事**：作为 QA/User，我希望验收发现缺陷后可指派、返工、复核，以便缺陷闭环。

**交互流程**：
1. QA 验收按 AC 逐条核对（映射 `qa/cases.md` 验收用例 + `qa/test.md` 记录）；发现缺陷 → 写《缺陷文档》并登记产物 → `wb_comment(domain=rd|fe)` 程序自动指派缺陷负责人（L1/L2 可归属时无需 domain）。
2. RD/FE 处理：真缺陷修复 → `resolve(note=修复说明)`；认为误判/非缺陷 → **直接 `resolve(note=理由)`**（带理由解决即异议表达，**不存在"RD 打回 QA"**）。
3. QA 复核（**最终裁定**）：认可（修复 OK / 理由成立）→ `confirm` 缺陷关闭；不认可修复结果 → `reopen`（即"QA 打回对方解决"），RD/FE 继续。
4. QA 重跑自动化回测（`qa/data/` + `qa/code/` 落代码，一键复跑）；全部缺陷闭环后门禁放行。

**业务规则**：
- **与流程级打回区分**：评论 `reopen` = 单条缺陷不认可修复；`wb_decide reject(targetBranch)` = QA 验收**整体打回开发阶段**（部分回滚，仅回滚对应分支）。两者裁决层级不同。
- 缺陷归属：纯前端/后端需求通常落 L1（产物作者唯一）不走 L3；跨端根因不明时 QA 输出 `domain=rd|fe` 驱动自动指派（详见 `arch_design.md` §9.3）。

**验收标准（AC）**：
- [ ] Given QA 发现缺陷, when 登记并传 domain, then 程序自动指派 RD/FE。
- [ ] Given RD/FE resolve 带理由, when QA 复核, then confirm 关闭 / reopen 继续。
- [ ] Given 缺陷打回, when QA 触发, then 仅对应分支回滚（部分回滚）。
