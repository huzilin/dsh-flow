## 1. 问题陈述（为什么做）

### 1.1 现状与证据

流程推进、评审、评论会产生大量「需要 User 回应」的事件。若无统一入口，User 会错过待评审门禁、待界定范围、待回复对话。

### 1.2 影响与代价

缺乏收件箱 → 待办遗漏、评审卡死；缺乏 TODO → 待办无法聚合呈现、输入框旁无常驻视图。

### 1.3 时机与约束

模块 III/IV 依赖模块 II 的事件；收件箱为 User 全局（跨项目聚合）。

## 2. 目标与成功指标

### 2.1 业务结果指标

| 指标 | 当前基线 | 目标值 | 观察周期 | 数据口径 |
|---|---|---|---|---|
| 待办可见性 | 无 | 任何需 User 回应的沟通进收件箱 | — | 六类条目 |
| 可操作性 | 无 | 收件箱/ TODO 可点击跳对应节点 | — | 点击跳转 |

### 2.2 交付结果指标（护栏 Guardrails）

| 指标 | 底线要求 |
|---|---|
| 不预存通知表 | 收件箱条目是 tasks/issues 的查询投影（决策 3） |
| 断点续接 | dispatch_at/last_ack/last_progress/resume_hint 支撑重启续接 |

## 3. 范围与非范围

| 分类 | 内容 |
|---|---|
| **Must** | 收件箱六类条目、badge/toast + 未读数、全局聚合 + 两层筛选、逐条可回应、TODO 四类条目 + 输入框 dock |
| **Should** | 断点续接、待回复实时推导 |
| **Not now** | 多项目切换 UI（E3 聚合后置） |

## 4. 用户与场景

### 4.1 用户角色

| 角色 | 特征 | 目标 |
|---|---|---|
| User | 全局协调者 | 处理待评审门禁、待界定范围、待回复对话 |

### 4.2 主路径

评审门禁触发 → 收件箱 badge/toast + 未读数 → 点击进入收件箱列表 → 项目×任务名两层筛选 → 条目点击跳对应节点评审区 → 在原上下文中回复/表态/关闭 → TODO 作为常驻投影呈现未完成工作。

### 4.3 高频异常场景

- 收件箱消息多 → 靠两层筛选聚合不淹没。
- 重启后任务中断 → 扫「已派未确认」「进度陈旧」续接，不重来。

## 5. 功能需求

### 5.1 功能总览

| 功能模块 | 优先级 | 描述 | 状态 |
|---|---|---|---|
| 收件箱（模块 III） | P0 | 六类条目 + badge/toast + 未读数 + 两层筛选 | 待开发 |
| TODO 列表（模块 IV） | P0 | 四类条目 + 输入框 dock + 未完成数+分类聚合 | 待开发 |

### 5.2 功能详细说明

#### 收件箱条目类型（六类）

| 类型 | 触发 |
|---|---|
| 待评审门禁 | 节点进入「待评审」 |
| 待界定新范围 | 打回理由引入新范围，边界待 User 界定 |
| 产出修订完成 | 产出者按打回意见修订完毕，待复验 |
| 产出者反驳 | 产出者就打回意见提出异议 |
| 要求补充答复 | 产出者发现 User 答复有遗漏，要求补充 |
| 对话待回复 | 任一方向有未回复沟通 |

**用户故事**：作为 User，我希望任何需回应的沟通都进收件箱，以便逐条必办。

**验收标准（AC）**：
- [ ] Given 节点进入待评审, when 状态变更, then 生成「待评审门禁」条目并提示未读。
- [ ] Given 打回带新范围, when 界定前, then 生成「待界定新范围」条目。
- [ ] Given 对话有未回复, when 产生, then 生成「对话待回复」条目。

#### 收件箱呈现与筛选

**用户故事**：作为 User，我希望收件箱可聚合、可筛选、可点击进入。

**交互流程**：`shell.overlay` badge/toast + 未读数 → 点击进收件箱列表 → 两层可叠加筛选（项目筛选 × 任务名筛选）→ 条目点击跳对应节点评审区。

**业务规则**：收件箱为 User 全局（跨项目聚合）；每条目冗余 `projectId` + `requirementId/requirementTitle`，查询按此过滤/搜索，免跨文件 join。

**验收标准（AC）**：
- [ ] Given 收件箱有未读, when 渲染, then badge/toast 显示未读数。
- [ ] Given 项目×任务名筛选, when 叠加, then 展示交集条目。
- [ ] Given 点条目, when 操作, then 跳对应节点评审区。

#### TODO 列表（模块 IV）

**用户故事**：作为 User，我希望输入框旁常驻 TODO，以便一眼看清未完成工作。

**交互流程**：`conversation.input.dock` 常驻 → 以「未完成数 + 分类」聚合 → 点击条目跳对应节点。

**业务规则**：四类条目（待评审节点/待界定新范围/打回后等待修订/我的意见待回复·待补充答复）；TODO = 收件箱的操作投影（同源、同筛选，呈现粒度不同）。

**验收标准（AC）**：
- [ ] Given 有待办, when 渲染, then 输入框 dock 显示未完成数 + 分类聚合。
- [ ] Given 点 TODO 条目, when 操作, then 跳对应节点。
