## 第一段：概念对齐（10 分钟）——三个断言，逐条"同意 / 不同意 / 补定义"

| # | 断言 | 主稿出处 |
|---|---|---|
| 1 | 插件 = 能力注入者（挂在 context 上：工具 / 服务 / 事件 / UI slot / 路由 / 可逆 effect）| §0、§1.3、§3 |
| 2 | agent（主 agent）= 回合循环 + Session 状态；顶层 agent（无 parentSession）≈ 主 agent | §1.1 |
| 3 | subagent = 委托机制（一个 agent 创建出**另一个完整 agent**），不是第三种实体；**角色是数据不是实体**（`wb_my_task(reqId, role)` 的 role 是参数）| §1.2、§8.2 |

**第一段分歧点**：你说的"主 agent"是 UI 会话角色，还是 `roots()` 顶层 agent？headless / Ralph / ACP 接入的算不算"主"？（开放问题 1）

## 第二段：多个主 agent 并行时，插件如何交互（10 分钟）——三个规则 + 实锤

| # | 规则 | 主稿出处 |
|---|---|---|
| 1 | 隔离的根在 **scope**（对象身份），不在进程：单进程承载所有并行 agent（本机 8 个 workdir 会话同挂 web profile）| §4.1、§4.2 |
| 2 | 工具全局一份 → **唯一跨 agent 通道 = 全局注册**（组件开关/服务状态影响所有会话的下一轮装配）| §4.4 |
| 3 | 动态插件按 session 归属但运行态共享进程内存；UI 页级；**子 agent 全新扁平 scope、默认不继承父插件注册**（传能力要 `agentPresets.composeFrom`）| §4.2、§4.3 |

**实锤**：你 profile 的 20 个插件已逐个分类（§4.6）——工具类全局、UI 类页级、auto-continue 是"进程一引擎 + `agent.followup` 续跑"、memory-plugin 有 recall 作用域开关（`all`/`actor`）、dsh-approve 是"宿主数据 + 客户端 slot"双层。

## 第三段：落到你的工作台系统（10 分钟）——三个对应 + 一条分叉

1. **执行闭环不用自建**：你们的"agent→subagent→再调度"= DSH 原生 `followup` / `interrupt` / `reportFrom`（§8.2）。
2. **角色隔离保持数据层**：scope 管"工具存不存在"，wb_my_task 管"工具返回什么"——两层互补（§8.2）。
3. **组级隔离三条路**：现实路径 0（多进程 / 多 profile，今天可用）；设计素材 A preset 约定 / B scope key 泛化 / C restriction 配置化（§4.7）。我的倾向：先定问题规模再选路。

**第三段分叉**：角色隔离放哪层？保持数据层路由，还是部分工具按角色 scope 隔离？（开放问题 7）
