## 1. 目标与范围

**目标**：交付需求详情页 = OA 流程树视图。User 在此评审产出物、与产出者多轮对话、推动需求在各阶段流转；门禁是流程推进的卡点。

**范围内**：

- 流程树：节点独立，通过前进、打回回退；
- 评审：评审状态行（角色药丸）+ 展开角色「意见 ↔ 反馈」对话区；
- 产物阅读器：飞书式弹窗，支持文档级 / 行级 / 范围级 / 块级锚点评论；
- 门禁：通过（含前置校验）/ 打回（必填理由 + 可选新范围界定）/ 强权干预；
- 配套规则：行级锚点防漂移、评论解决状态机（复用 `05` §3.2）、已解决评论折叠、远端 GitHub CR 简化。

**范围外（后置/他模块）**：版本看板、需求池、创建需求 UI（模块 I）；收件箱、TODO（模块 III/IV）；diff 级锚点与代码 git-review 行内评论；多项目切换 UI。

## 3. 界面与交互（需求）

### 3.1 流程步骤列表（左列）

- 竖向列出流程实例全部节点，**全展示不折叠**（含已通过/未开始），节点按流程序排列；
- 每节点一行：状态圆点（绿 = 已通过 / 黄 = 进行中|待评审 / 灰 = 未开始）+ 节点名 + `↩N`（回滚 N 次）；
- **节点独立**：一条流程标签 = 一个节点，可独立回退重入；点击行切换右列详情；
- **前进/回退**：通过 → 前进下一节点；打回 → 回退上一节点（并行组内打回按 `targetBranch` 部分回滚，见 `05` §3.1 注）。

### 3.2 节点元信息卡

负责人（执行者角色）、进入时间、回滚次数、职责（职责文案文本展示）。无 `reviewers` 的节点不展示评审状态行，无 `gate` 的节点不展示门禁区。

### 3.3 评审状态行与角色对话区（有 `reviewers` 的 review 节点）

- **一行角色药丸**：`Architect ✅` / `RD ✅` / `FE ⚠2 未解决` / `QA ⚠轮14`；**轮次 ≥ 10 且未解决 → 药丸黄色高亮「疑似卡死」**。
- **点角色药丸 → 展开该角色「意见 ↔ 反馈」对话区**：该角色名下每条评论是一条对话串（评审者提意见 → 产出者反馈 → 可多轮，`roundCount` 累计）。
- **User 三态参与**：
  1. **参与讨论**：在任一评论下「回复」；
  2. **普通 resolve**：把某条评论标「解决」（见 §3.7 判定矩阵）；
  3. **强权 override**：对话区底部「强行通过 X 全部剩余」按钮，把该角色所有 open 评论置 `overridden`。
- **评审通过 = 该角色名下全部评论均 `resolved`/`overridden`**（角色状态为派生值，不落库）。

### 3.4 产物区

- 节点绑定的产物以文件行展示：文件名（点击打开阅读器）+ 设计理念注记（note）+ `💬N`（该产物评论数）；
- `kind=link` 的产物以新窗口跳转打开（不进入阅读器）；`kind=document` 打开产物阅读器；
- 无产物的节点显示占位提示（如「尚无产物」），不拦流程 UI。

### 3.5 产物阅读器（弹窗）

- **布局**：弹窗约 72vw × 85vh；**正文占满宽度（无右侧栏）**，底部固定一条输入框（见 §3.6 文案规则）。
- **轻量 markdown 渲染**：标题 `#`~`######` 放大加粗；粗体 `**text**`；行内代码 `` `code` ``；围栏代码块整体渲染（等宽、深色底、顶部语言标签如 mermaid/json）；**mermaid 仅按代码块展示，不画图**；列表/表格/引用暂不实现。
- 每行左侧灰色**行号**（1-based），行号为锚点与评论定位的基础。

### 3.6 锚点选择交互（权威规则）

1. **单击一行** = 单行选中（黄色高亮），可直接发表单行评论；
2. **点其他行** = 框选范围（起点 ~ 该行高亮区间）；
3. **重复点起点行** = 取消选择；
4. **框选后（已完成 1~3）再点任何行 C** = **重新开始**，仅高亮 C（不再扩展终点）。

底部输入框文案随选中状态变化：单行「对第 N 行评论」/ 范围「对第 A~B 行评论」/ 无选择「写文档评论…」。

### 3.7 评论展示与操作

**锚点四级的展示位置**：

| 锚点 | 展示位置 |
|---|---|
| `line` | 对应行下方内嵌（一一对应） |
| `range` | **只在末行（endLine）下方显示一次**，卡片带 `↔ A~B 行` 标记；**点击标记 → 高亮整个范围**（独立视图高亮，不干扰新建选择） |
| `block` | 代码块下方 |
| `document` | 正文末尾 |

**高亮规则**：有评论的行/块 = 浅蓝背景 + 左侧色条；正在选中的行/范围 = 黄色。

**评论卡片**：作者 + 文本 + 状态标（`未解决`/`已解决`/`已强制通过`）+ `roundCount`；open 态常驻「回复」输入框 + 「解决」按钮；**已解决（`resolved`/`overridden`）默认折叠**成一行摘要（作者 + 文本截断 + 状态标 + ▸），点击展开、展开后可「收起 ▴」。

**UI 操作判定矩阵**（一条评论的操作面板按状态 × 操作者动态渲染）：

| 评论状态 | 操作者 | 可操作 | 判定 |
|---|---|---|---|
| open | 任何人 | **回复** | 继续讨论/提问/澄清，状态不变（`roundCount++`） |
| open | **assignee**（缺省 = 锚定产物作者；QA 缺陷 = 显式指派 RD\|FE） | **resolve（A 修复关闭）** | 已修复 → 填 note → 转 `pending-confirm` |
| open | **提评者**且讨论已一致 | **resolve（B 协商一致关闭）** | 达成一致 → 填 note，直接 `resolved` |
| open | 非 assignee 非提评者 | 仅回复 | 表达意见，等 assignee/提评者收尾 |
| pending-confirm | **提评者** | **confirm / reopen** | 最终裁定（复核不通过 reopen → open） |
| pending-confirm | 非提评者 | 只读 | 等待提评者复核 |
| resolved / overridden | — | 只读 | 可展开查看 resolve 记录（by/note/path） |

- 判定一句话：**reply** = 评论未关还想说；**resolve** = 要关——你修复了（A）或谈拢了（B），必须填 note；**confirm/reopen** = 已 resolve 过、你是提评者做最终裁定。
- **User（协调者）特判**：可代任一身份操作（代 assignee 走 A、代提评者走 B 或 confirm/reopen），**操作前须指明扮演角色**（操作归属记到被代者名下），避免身份混淆。
- 评论**不可编辑/删除**；误发用 reply 标注「作废」（审计留痕）。

## 4. 数据与规则（设计）

### 4.1 文件结构与实体

```
<workspace>/.workbench/
  requirements.json        # 项目级：需求列表
  <reqId>/
    flow.json              # 流程实例 + 节点（FlowNode，含 reviewers[]）
    artifacts.json         # 产物（文件行）
    comments.json          # 统一评论模型（评论 = 问题，四级锚点）
```

- 实体字段以 `05-domain-model.md` §2 为唯一真相源（本文不重复字段表）：Version / Requirement / Flow + FlowNode / Issue / Artifact / Task / 支撑表。
- 关键对齐点：`reviewers[]` 仅静态声明 `[{role, capability_id, scope?}]`，动态「谁过了没」由评审表态 + 评论闭环派生；评论 = 问题统一模型（不区分评审 Issue 与普通评论）。

### 4.2 节点通过门禁判定

- **门禁 = 该节点名下全部评论闭环**：无 `open`、无 `pending-confirm`，且全部 `resolved`（`reviewer_confirmed=true`）或 `overridden` 才可「通过」（状态机转移表见 `05` §3.2，不重写）。
- UI 常驻展示 `已解决/总数`（如 `2/6`）；**未满时「通过」置灰/拦截**，防止处理中还误通过。
- 有 `reviewers` 时额外派生：**每个 reviewer 状态 = 其名下评论全部闭环**才算「已通过」——角色粒度是评论的归属统计维，与节点门禁是两回事。
- 「通过」为终审动作：前置校验通过后节点 → 已通过，`current_node_id` 前移下一节点。

### 4.3 评审两阶段闭环

- **角色评审在前、User 终审在后**：角色评审者只对自己职责内维度评审表态（各审各的）；User 终审（`decide`）前置校验 §4.2 门禁。
- **User 可随时介入**：参与讨论、普通 resolve、强权 override——不等待角色评审自然结束。
- **override（强行通过）与 forceRevise（强制修改）由 User 明确指令触发，产出者不可异议**；`override` 对评论/整角色，`forceRevise` 对节点发修改令。

### 4.4 行级锚点防漂移

- 行级锚点记录 `line`（绝对行号，1 起）+ `lineText`（该行**去首尾空白后的原文**，作定位指纹）。
- **指纹不用密码学哈希**：Host Builtin 已核实无 `crypto`/`Buffer`/`process.getBuiltinModule`，仅 `btoa`/`atob`/`TextEncoder`；直接用去空白原文，**字符串相等即命中**。
- **定位策略四步**（渲染阅读器时）：
  1. 按 `lineText` 在当前文档反查内容相同的行；
  2. 命中 → 锚定到该新行号；
  3. 未命中 → 按 `line` 就近展示，并标「⚠ 锚点可能失效」；
  4. 用户重新确认时更新 `line`/`lineText`。

### 4.5 远端 GitHub CR 简化方案

- **决策：远端评审结论本地化——无远端评论、无双向同步**；GitHub 仅作为 CR 信息来源（CR 在远端看代码，把结论落到工作台）。
- CR 结论落地方式：Leader/CR 子 agent 在工作台落一条本地评论（author=Code Reviewer，nodeId=开发节点，anchor=MR link 或开发说明，text=评审结论：通过/阻塞问题清单）→ 开发者按评论修复 → `resolve(note)` → CR 复核 `confirm` → `wb_review pass`。
- 评论模型保持单一来源：工作台评论 `source` 恒为 `workbench`，不设远端字段；GitHub 行级上下文在评论 text 中体现（如 `path:line`）。

### 4.6 超时与拉锯

- **拉锯升级**：`roundCount > 5` → 自动通知 Leader/User 介入（防无限拉锯）。
- **待复核超时提醒**（轮询，每 5 分钟）：`pending-confirm` 挂起超时 → 提醒提评者复核；**提评者 = User → 阈值 1 小时；提评者 = agent → 阈值 5 分钟**；挂起期间不阻塞其他评论/流程（仅超时提醒）。

## 5. Host RPC（`harness.handle` 的 `wb.*`）

> 所有方法返回**该需求最新聚合快照**（纯 JSON、lossless），Client 直接用于重渲染；写冲突处理：**M2 单用户读-改-写，无并发锁**（`fs` 全量覆盖对应文件），并发锁后置。

| 方法 | 一句话语义 |
|---|---|
| `wb.getRequirement` | 读需求聚合快照：requirement + flow + artifacts + comments |
| `wb.getArtifactContent` | 读产物文件正文（供阅读器渲染与锚点定位） |
| `wb.comment` | 追加一条 open 评论（可带任一级锚点、归属角色） |
| `wb.reply` | 评论下追加对话（任意参与者，`roundCount++`） |
| `wb.resolve` | 关闭评论：A 路径 → `pending-confirm`，B 路径 → `resolved`（须带 note/path） |
| `wb.override` | 评论或整角色评论 → `overridden`（User 强权，绕过门禁） |
| `wb.decide` | 门禁终审：pass（校验全评论闭环）→ 前进；reject（reason 必填）→ 回退 + 可选 `pendingScope` |
| `wb.forceRevise` | 记强制修改令（产出者不可异议） |
| `wb.defineScope` | 关闭 `pendingScope`，写入新范围边界 |
| `wb.review` | 角色评审表态 pass（pre 校验：无 open + 无 pending-confirm + 全 resolved 且复核确认） |
| `wb.confirmReview` | 提评者复核确认：`pending-confirm` → `resolved`（校验调用者 = 提评者） |
| `wb.reopen` | 提评者复核不通过：`pending-confirm` → `open`（`roundCount++`，通知 assignee） |

- 同一套 `op*` 领域函数被 UI RPC 与模型工具共用（同一审计/门禁/状态机）；未满足门禁时 `decide`/`review` 返回 `blocked` 而非静默通过。

## 6. 定稿要点

1. 左列节点**全展示不折叠**，节点独立（一条标签一节点），通过前进、打回回退上一节点。
2. **评论 = 问题统一模型**（无「评审 Issue / 普通评论」之分），不可编辑/删除（误发用 reply 标注作废）。
3. 锚点**四级**：`document / line / range / block`（章节 heading 级已废弃，diff 级后置）。
4. 行级锚点防漂移：`line` + 去空白 `lineText` 原文指纹（无 crypto，字符串相等命中）四步定位，失效标「⚠ 锚点可能失效」。
5. **评审两阶段闭环**：角色评审在前、User 终审在后、User 可随时介入；`override`/`forceRevise` 不可异议。
6. 评审状态行 = 角色药丸 + 点开「意见 ↔ 反馈」对话区；User 三态 = 参与讨论 / 普通 resolve / 强权 override；评审通过 = 该角色评论全闭环。
7. 解决状态机：A 修复关闭需提评者 `confirm` 才放行；B 协商一致由提评者直接关闭；`confirm`/`reopen` 仅限提评者（不能自确认）。
8. 门禁判定 = 无 open + 无 pending-confirm + 全 resolved（复核确认）或 overridden；UI 显示 `已解决/总数`，未满置灰拦截。
9. 阅读器飞书式：整行可点、行内嵌评论、有评论行高亮、正文占满宽度、底部输入框；mermaid 按代码块展示不画图。
10. 行选择四规则：单击 = 单行、点其他行 = 框选、重复点起点 = 取消、框选后再点 = 重新开始；输入框文案随选中变化。
11. 范围评论只在末行显示一次 + `↔A~B` 标记点击高亮；已解决评论默认折叠为一行摘要。
12. 远端 CR 结论本地化落工作台评论，无双向同步，评论模型单一来源。
13. 拉锯升级：`roundCount > 5` 通知 Leader/User；复核超时提醒 User 1h / agent 5min（轮询每 5 分钟）。
14. 写冲突：M2 单用户读改写无锁，每次写返回最新聚合快照。
