# M6 PRD：团队制度层（Team Preset）

> 状态：**v1.0（定稿）** — 制度层以 **DSH agent preset** 形式落地：团队内任何 agent 会话（本会话 + 未来子 agent）加载同一份制度，执行层（wb_* 工具）与交互层（工作台 UI）共用同一套领域逻辑。
>
> v1.0 变更：① 业务需求流程重写为 12 节点（产品设计 → 需求评审 → RD 技术设计 → RD 技术评审 → FE 技术设计 → FE 设计评审 → 用例设计 → 用例设计评审 → RD 开发 ∥ FE 开发 → QA 验收 → 用户验收，无产品设计评审独立节点、设计阶段串行、仅开发并行）；② 所有流程新增通用首阶段「待启动」；③ 任务流程首阶段更名「需求对齐」；④ 评审职责分工铁律；⑤ QA 验收产物含《测试用例与结果》。

## 1. 定位与架构

四层架构中「制度层」的正式落地：

| 层 | 载体 | 状态 |
|---|---|---|
| 制度层 | **team preset**（DSH agent preset，含 skill） | M6 本里程碑 |
| 交互层 | workbench 插件（wbflow-1） | ✅ 已完成（pkg-34） |
| 数据层 | `<workspace>/.workbench/` | ✅ 已完成 |
| 执行层 | 16 个 wb_* 模型工具 | ✅ 已完成（pkg-24） |

- preset 从 **standard** 复制（非 cordis），在其上**叠加团队制度**：角色、流程、门禁、协作铁律、skill 指南
- 制度 **只读**：团队成员的 agent 会话遵循 preset 规定行事；要调整制度，由 User 明确指示后改 preset 文件
- preset 决定：该会话挂哪些工具、系统提示里有哪些制度内容、可加载哪些 skill

## 2. 团队模型（9 角色）

| 角色 | 职责 | 典型 owner 场景 |
|---|---|---|
| User | 需求提出方 / 最终决策者，制度唯一修改入口 | 确认范围、拍板发布 |
| Leader | 团队负责人，拆解任务、分派 owner | 版本规划、需求分派 |
| Investigator | 调研/澄清需求，输出调研结论 | 需求前置调研、澄清 |
| Architect | 技术方案设计与评审 | 技术设计、方案把关 |
| RD | 后端研发 | 服务/计算类需求实现 |
| PM | 项目管理/范围管控 | 排期、进度跟踪 |
| FE | 前端研发 | 界面/交互类需求实现 |
| QA | 测试与验收 | 验收点核对、回归 |
| Code Reviewer | 代码评审 | 实现产物审查 |

角色与需求字段 `owner` 一致（需求表单 datalist 已含：User/Leader/Investigator/Architect/RD/PM/FE/QA；Code Reviewer 作为评审角色出现在流程门禁）。

## 3. 流程类型与节点

按需求 `category` 区分流程模板（与数据层 flow.json 对应，M7 真实子 agent 编排时按此生成）。**每节点标注：谁（角色）做什么 → 产物 → 门禁**。各流程的评审职责分工明细见 `m6-flow-templates.md`。

> **通用首阶段「待启动」**：所有流程（需求任务/任务/版本规划）第一个节点均为 **待启动**——表示需求已创建但尚未投入资源；当团队**开始投入资源**（决定启动该需求/任务/版本）时，将「待启动」推进到下一阶段。owner=Leader，无门禁（启动动作本身）。

### 3.1 需求任务（category=需求任务）

**需求来源（两条）**：
- ① User 直接建到需求池（用户诉求）
- ② Architect 做版本规划时拆分/扩展的派生需求
- **排期前置铁律**：无论来源，正式排期（归入大版本）前**必须有架构文档作为输入**；正式启动时 **Architect 将架构文档贴入需求描述**（链接或正文）——制度写入 preset

**需求子类与属性**：
- 新增 `reqType` 字段：**业务需求 / 技术需求**（纯后端/纯前端不再是独立类别，而是业务需求的 scope 特例）
- 新增 `scope` 字段：**仅前端 / 仅后端 / 前后端都含**（`scope` 控制 FE/RD 相关节点是否出现）
- **owner 规则**：`scope=仅前端` → **FE**；其余（仅后端、前后端都含）→ **RD**（RD 主导，FE 按需并行）
- `reqType`/`scope` 只存字段，不做筛选

#### 业务需求（reqType=业务需求）— 11 节点 + 待启动，scope 控制 RD/FE 侧节点

> 顺序（User 定稿）：产品设计 → 需求评审 → RD 技术设计 → RD 技术评审 → FE 技术设计 → FE 设计评审 → 用例设计 → 用例设计评审 → **RD 开发 ∥ FE 开发（并行）** → QA 验收 → 用户验收。**无产品设计评审独立节点**（产品方案把关并入需求评审）；设计阶段串行；仅开发阶段并行。
>
> scope 特例：`仅前端`（owner=FE）→ 跳过 RD 技术设计/RD 技术评审/RD 开发；`仅后端` → 跳过 FE 技术设计/FE 设计评审/FE 开发。

| 节点 | 谁 | 做什么 | 产物 | 门禁 |
|---|---|---|---|---|
| ⓪ 待启动 | **Leader** | 需求已创建未投入资源；**开始投入资源**时推进到下一阶段 | — | —（启动动作本身） |
| ① 产品设计 | **架构师** 主导 | 产品方案：交互、信息架构、页面结构 | 《产品设计文档》 | —（产出后由需求评审把关） |
| ② 需求评审 | **PM** 主导；架构师/User 参与 | 评审需求合理性 + 产品方案；疑问与架构师、User **确认拍板** | 评审结论 | **PM 确认** + User 参与拍板 |
| ③ RD 技术设计 | **RD** 主导（`scope=仅前端` 时无此节点） | 后端技术方案：接口、数据、模块、依赖 | 《RD 技术设计》 | — |

| ⑥ FE 设计评审 | **FE** 发起 | 评审 FE 方案 | 评审意见 | **QA** |
| ⑦ 用例设计 | **QA** 主导 | 明确前后端各自自测什么、如何联调 | 《用例/联调设计》 | — |

| ⑪ 用户验收 | **User** | 最终验收，任务结束 | — | **User** |

**QA 打回规则（节点 ⑩）**：发现 bug 打回给具体 bug 方（RD 或 FE），**部分回滚**：若只有 FE bug，RD 的开发保持通过，仅 FE 回滚到开发中；全部通过 → 进入用户验收。

## 4. 门禁与评审（复用 M2 状态机）

- 每个门禁节点：`wb_comment` 提问题 → `wb_reply` 讨论 → `wb_resolve` 解决 → `wb_decide pass/reject`
- 未全 resolved 时 pass 被拦截（blocked）；reject 打回上一节点（reason 必填，可勾选重新界定范围）
- override 属强权操作，仅 User 明确指令可用（工具描述已标注）
- 并行组（业务需求 ⑨.1/⑨.2）join 语义：两分支均通过后才放行下一节点（M7 状态机升级）

### 4.1 评审职责分工（铁律：各审各的）

**每个评审节点，各评审者依据自身角色职责，只对自己负责的部分做主要审核与把关，不越界包揽。** 评审者的评论应落在其职责范围内的内容上，`pass` 决策也按此判定。各角色职责与节点级分工见 `m6-flow-templates.md`（每类流程后附「评审职责分工」明细）。

通用角色评审口径速查：

| 评审者 | 主要审什么（职责内） |
|---|---|
| User | 方向/目标是否符合预期、是否可交付/可关闭 |
| PM | 需求价值、优先级、范围、排期与依赖 |
| Architect | 技术路线、方案可行性、与总体架构的一致性 |
| RD（设计方） | 设计完整性、接口/数据、自测方案 |
| FE（设计方） | 交互可实现性、组件/状态方案 |
| QA | 可测性、用例覆盖、验收口径、缺陷闭环 |
| Code Reviewer | 代码质量、设计落地、回归风险 |
| Leader | 范围与资源、版本目标 |

> 落地：评审节点中某评审者若对其职责范围外的事项有异议，应提出供参考，但**不作为该评审者 pass/block 的判定依据**；其职责内问题未解决则该评审者不 pass（计入门禁拦截）。

## 5. 协作铁律（制度内容，写入 preset 系统提示）

1. **文档先行**：PRD → 技术设计 → 原型 → 实现 → 回写文档（M4 教训固化）
2. **小步多确认**：每里程碑先产出产品文档/原型，User 确认后再实现
3. **feature branch + MR**：代码/文档改动走分支评审（文件锁已去掉）
4. **审计即证据**：需求字段变更自动写 history（谁将什么从什么变更为什么）；流程节点状态由 decide 驱动，不手改数据
5. **破坏性操作确认**：删除需求/废弃版本/强权通过，必须 User 明确指令
6. **验收闭环**：每个需求有验收点，QA 核对（附《测试用例与结果》）后 User 确认才算完成
7. **同一 feature 分支**：分支名在 RD 技术评审（业务/技术需求）或方案评审（任务）阶段**敲定**（`feature/<需求id>-<主题>` / `fix/<需求id>-<主题>`），后续 RD、FE、QA、Code Reviewer **全程看同一分支**，避免各自分支难对齐
8. **多任务并行用 worktree**：并行开展多个任务时，每个任务在独立 **git worktree**（各自分支）中修改，互不阻塞、互不污染工作区；单任务串行时可普通分支
