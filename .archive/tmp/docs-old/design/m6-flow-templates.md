# M6：流程模板表（阶段 / 负责人 / 做什么 / 输入 / 产物 / 审批者与审核重点）

> 状态：**v2.0（按 v1.0 PRD 全面重写：业务需求 12 节点、通用首阶段「待启动」、任务首阶段「需求对齐」、评审职责分工、QA 验收产物含《测试用例与结果》）；v0.28 口径对齐——业务需求 = 12 业务节点 + 待启动（并行开发按 m8/seed 口径算 2 行）**
> 列定义：**阶段**（节点）→ **负责人**（谁做）→ **做什么** → **输入**（依赖什么）→ **产物**（产出物，doc=文档/link=链接/—=无）→ **审批者**（门禁谁审）→ **审批者主要审核**（审什么）。
>
> **通用首阶段「待启动」**：所有流程第一个节点为「待启动」（owner=Leader，无门禁）——需求已创建未投入资源；团队开始投入时推进到下一阶段。以下各表不再重复列出，实际 flow 均以「待启动」开头。

## 附：产物文档模板（各阶段 doc 类产物必含小节；写入 skill 指南）

> 原则：每份产物文档既要服务本阶段产出，也要为**下游审批角色**提供其职责内所需信息（各审各的）。

### 1. 《产品设计文档》（业务需求 ① 产品设计，Architect）
1. 目标与范围（对齐需求描述）
2. 交互与信息架构（页面/流程/状态）
3. 验收点（可核对，QA 可测性输入）
4. 开放问题（待需求评审澄清）

### 2. 《RD 技术设计》（业务需求 ③ / 技术需求 ②，RD）
1. 方案概述与目标
2. 接口/数据设计（FE 评审接口契约依据）
3. **工期与依赖**（PM 评审排期依据；外部系统/第三方依赖明列）
4. 自测方案（QA 联调口径）
5. 风险与回滚

### 3. 《FE 技术设计》（业务需求 ⑤ / 技术需求 ④ 按需，FE）
1. 组件与状态方案
2. 关键路径与交互实现（QA 可测性输入）
3. 接口调用契约（对照 RD 设计）
4. 自测与回归口径

### 4. 《用例/联调设计》（业务需求 ⑦ / 技术需求 ⑤，QA）
1. 各端自测用例（RD/FE 各自测什么）
2. 联调用例与口径
3. 验收用例（QA 验收用，可执行）
4. 回归范围

### 5. 《方案文档》（任务 ② 方案评审，执行者）
1. 问题根因/目标
2. 方案（怎么修/怎么做）
3. 改动范围与回归影响（QA 可测性输入）
4. **feature 分支约定**（`fix/<需求id>-<主题>`）

### 6. 《测试用例与结果》（QA 验收，QA）
1. 用例清单（用例/步骤/预期/结果表格）
2. 执行结果与缺陷记录
3. 结论（通过/遗留问题）

### 7. 《缺陷文档》（QA 验收发现 bug 时，QA）
1. 缺陷清单（现象/复现/归属端 rd|fe/状态）
2. 打回对象与部分回滚依据

### 8. 《需求对齐文档》（版本规划 ①，Architect）
1. 版本方向与范围
2. 候选需求清单（版本内需求/上版本路线）
3. 待确认问题

### 9. 《调研文档》（版本规划 ②，Investigator）
1. 竞品/开源方案对比（GitHub 等）
2. 结论依据（数据/来源）
3. 建议：引入 or 重写，为什么

### 10. 《架构规划》（版本规划 ③，Architect）
1. 版本目标（短板、本期解决、分期）
2. 引入/实现能力
3. **需求拆解清单**（供 ④ 创建需求）

### 11. 《需求清单》（版本规划 ④，Leader）
1. 拆解出的需求（类别/归属版本/状态）
2. 与架构规划对应关系

## 附：flow.json 节点字段（含分支约定）

- `id/key/order/ownerRole/gate/state/enteredAt/rolledBackAt[]`：既有字段
- `reviewers[]`：`{role, state, commentIds[]}` 评审者与状态
- `branch`：泳道（`rd`/`fe`，仅并行开发组用，用于流程图双行布局）
- `parallelGroup`：并行组标识（业务需求 `dev-1` = RD 开发 + FE 开发；组内各分支完成后才放行下一节点）
- **`featureBranch`**（新增）：feature 分支名（`feature/<需求id>-<主题>` / `fix/<需求id>-<主题>`），在 **RD 技术评审（业务/技术需求）或方案评审（任务）** 节点敲定后写入，同一需求后续节点共用（开发/CR/QA 均看该分支）
