## 1. 调研背景与目标

### 1.1 背景

售后模块需要多级审批流（按金额分级：≤500 客服主管、≤2000 售后经理、>2000 风控+总经理会签），当前是硬编码 `if-else` 状态机，规则一变就要发版。业务预期后续审批流会频繁调整（加节点、改分支、加会签），因此要评估：**是否有开源流程引擎可直接引用，还是借鉴其思想自研一套轻量审批引擎**。

### 1.2 要回答的问题清单

- [x] 是否有功能匹配的开源流程引擎可直接引用？
- [x] 候选引擎各自的开源架构如何（嵌入式库 vs 独立服务、BPMN 支持度、扩展模型）？
- [x] 许可证、安全、社区健康度是否满足使用条件？
- [x] 直接引用 / 借鉴架构自研的代价分别是什么？
- [x] 引入后的集成、维护、合规成本？

### 1.3 判定标准（选型门槛）

| 维度 | 底线要求 |
|---|---|
| 功能匹配 | 核心场景（顺序/条件分支/会签/驳回）覆盖 ≥ 90%；缺失项可扩展 |
| 许可证 | 宽松协议（Apache-2.0/MIT）；公司产品为闭源商业化，**GPL 类一票否决** |
| 活跃度 | 最近 release 距今 < 6 个月；最近 1 年有实质提交 |
| 安全 | 无未修复高危 CVE；有安全响应流程 |

## 4. 开源项目评估（核心）

### 4.1 功能与需求匹配度

| 评估点 | Flowable | Camunda 8 |
|---|---|---|
| 功能满足度 | 高覆盖：BPMN 2.0、会签、驳回、条件分支全支持（≥95%） | 高覆盖：BPMN + DMN（决策）、云端优先（≥95%） |
| 性能满足度 | 吞吐中等，嵌入式无网络开销 | 分布式高吞吐，跨节点设计 |
| 可测试性 | 好（Java API、mock 友好） | 好（云端 API + 本地测试库） |
| 行业规范遵从 | 无相关行业强制规范 | 同左 |

### 4.2 项目健康度（社区与维护）

| 指标 | Flowable | Camunda 8 |
|---|---|---|
| 许可证 | Apache-2.0 | Camunda 自研社区许可证（含商业条款） |
| 最近 release | 2025-05（稳定月更） | 2025-04（稳定） |
| Star / Fork | 约 8k / 2.3k | 约 4.5k / 0.9k |
| 近期提交实质 | 活跃（新功能+修复） | 活跃 |
| 贡献者数量 | 100+ | 200+（含商业团队） |
| 文档质量 | 官方文档+指南完整 | 官方文档+示例丰富 |
| 治理 | 基金会/公司主导 | 商业公司主导（受控） |

### 4.3 许可证与合规

- **Flowable**：Apache-2.0，宽松、可闭源商用；历史为 Activiti 分支（许可证继承 Apache-2.0）；SCA 扫描依赖均宽松；
- **Camunda 8**：社区版为专有许可证（非 OSI），生产部署核心功能需商业授权条款确认；需法务审核；
- 结论：**Flowable 合规可直接用；Camunda 8 需法务确认且长期商业风险高**。

### 4.4 安全

- Flowable：历史 CVE 少，有安全政策与应急流程；依赖面中等（BPMN 解析等）；
- Camunda：商业团队维护，响应快；
- 结论：两者风险可控；Flowable 依赖扫描（OSSIA 工具）无高危。

### 4.5 集成与维护成本

| 评估点 | Flowable | Camunda 8 |
|---|---|---|
| 集成侵入度 | 嵌入式库，侵入低（starter 集成）；也可独立部署 | 独立平台 + 客户端 SDK，部署拓扑较重 |
| 扩展/定制 | 命令拦截器、监听器、扩展点丰富 | 依赖外部任务/操作 API，定制需学 Zeebe 模型 |
| 学习成本 | 中（BPMN 概念），中文资料多 | 高（新分布式模型） |
| 升级成本 | 版本间有迁移指南（但大版本迁移需评估） | 平台升级重 |
| 运维成本 | 轻（进程内） | 重（另起 Zeebe 集群） |

### 4.6 开源架构分析（读源码/架构结论）

**Flowable（嵌入式引擎架构）**
- 形态：Java 库嵌入业务进程，引擎与业务同进程；流程定义用 BPMN 2.0 XML；执行模型为"流程实例 + 令牌推进 + 命令拦截器"；
- 核心抽象：ProcessEngine / RepositoryService / RuntimeService / TaskService；扩展点：命令拦截器、事件监听器、自定义行为工厂；
- **与我们的契合**：技术栈同 Java/Spring；回调邀请码注入到既有订单服务改造小；
- **可借鉴点**：状态机推进模型、命令拦截器模式、审批任务模型；**不可直接复用点**：完整 BPMN 解析与部署框架对我们过重。

**Camunda 8（事件驱动编排架构）**
- 形态：独立 Zeebe 引擎（分布式、事件溯源存储），BPMN + DMN；worker 拉取外部任务；
- 核心抽象：Zeebe Gateway / Broker / Job Worker；可借鉴点：worker 任务模型（解耦任务执行）；不可复用点：集群版部署复杂度。

## 6. POC / 原型验证

- **验证目标**：① 审批流"金额分级 + 会签 + 驳回"能否 5 天内搭出；② 嵌入式对订单服务内存/启动影响；③ 规则变更是否需要发版。
- **验证环境与用例**：订单灰度环境 + Flowable 7 Starter；用 3 条典型审批流（≤500 / ≤2000 / 会签）跑用例。
- **验证结论**：全部用例通过；启动+80ms、内存 +120MB（可接受）；**审批规则变更只需改 BPMN/流程定义，无需发版** → 核心诉求达成。

## 7. 结论与建议

**结论**：推荐 **Flowable（嵌入式，v7.x）**，使用方式：**直接引入作为审批引擎**；审批流程定义用 BPMN 托管在引擎中，业务代码通过 API 驱动；不引入 Camunda（许可证与运维成本），不采用全自研（周期长、首版功能不够）。
**理由**：总分最高（4.4）、Apache-2.0 合规无忧、与 Spring 生态集成侵入度低、POC 验证核心场景 5 天落地且规则变更免发版。
**取舍**：放弃 Camunda 的分布式高吞吐与决策表能力（本版本并发与决策需求不强）；放弃自研的完全可控性（换取 2 个月交付周期）。
**本版本落地方式**：订单售后模块引入 `flowable-spring-boot-starter`，审批规则迁移为 BPMN 流程定义，硬编码状态机替换为引擎驱动；API 封装统一审批接口，业务侧无感知。
